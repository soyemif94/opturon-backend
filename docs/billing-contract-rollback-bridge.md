# BILL-006BC rollback bridge

## Base and scope

Base: `ffa90f8352abe2df515f228bdbe34e59959e732c` (BILL-006D production).
Branch: `fix/billing-contract-rollback-bridge`.

This precursor only protects marked nonterminal events from the older billing
executor. It adds no 6B routing, invoice search, financial comparisons, new
no-action policy, claim executor or short-transaction refactor. Production's
existing processing and timeout behavior remains in place for unmarked events.
It does not make the raw base commit a safe rollback target.

## Durable marker protocol

Storage: `saas_subscription_events.processingError`, existing nullable `TEXT`
from migration 050. The locked-event SELECT now exposes it; existing repository
writes already accept it. No schema change or data backfill is required.

Canonical format (ASCII, case-sensitive, maximum 85 characters):

```text
billing_contract_v2:claim:<lowercase UUID v4>[:<technical-reason>]
```

`v2` versions this internal processing protocol, not `metadata.contract.version`.
The claim ID must be generated by Node's existing `crypto.randomUUID()`. It is
not a timestamp, JS Date, provider ID, webhook body field or `Math.random()`.

The optional reason is exactly one of:

- `provider_timeout`
- `provider_network_error`
- `provider_5xx`
- `provider_not_found`
- `db_retryable`
- `claim_active`

There is no empty suffix, extra segment, whitespace normalization, arbitrary
exception text, provider payload or secret. Normal payment states and zero
invoice matches are deliberately excluded from the technical reason list.

`isBillingContractV2Marker()` validates the complete grammar, UUID version and
variant, maximum length and closed reason list. A prefix alone, `v20`, malformed
UUID, unknown reason or oversized value is not a marker. They retain historical
behavior. Future writers MUST validate with this parser before persistence;
malformed or newly invented formats do not receive this bridge's protection.
Protocol changes require a compatible precursor before any new writer deploys.

The bridge does not generate markers. The future 6BC runtime must write the
marker from its first durable claim and preserve it across every nonterminal
technical failure, including `received`, `processing` and `failed`. Claim-token
CAS and lease/reclaim logic belong to that future architecture correction.

## Guard position and behavior

Unchanged HTTP signature verification runs before the billing service. The
service inserts/finds the event and locks it with the existing BILL-005 flow.
Terminal handling stays first. For reprocessable states the guard runs before
`updateSubscriptionEventStatus(... processingStatus: 'processing')`, which would
otherwise set the absent `processingError` patch to NULL. It also runs before
the executor's first provider GET and before subscription/tenant mutations.

| Stored event | Bridge behavior |
| --- | --- |
| `received`, `failed`, `processing` + valid marker | HTTP 503; no provider GET, business UPDATE or event UPDATE; preserve the complete row |
| `processed` + marker | Existing duplicate HTTP 200; no provider GET or business mutation |
| `ignored` + marker | Existing duplicate HTTP 200; no provider GET or business mutation |
| `ignored` + 6D outcome | Preserve duplicate `MANUAL_REVIEW` / `CONTRACT_REJECTED` HTTP 200 |
| Nonterminal without valid marker | Unchanged production executor |
| Invalid signature | HTTP 401 before service/DB/guard |

The existing controller returns only
`{"success":false,"error":"webhook_processing_failed"}` on a bridge block.
The internal log is `billing_contract_v2_event_blocked_by_rollback_bridge`, with
no marker, claim ID or payload. Logging failure cannot bypass the guard.

This intentional 503 keeps protected events recoverable after the validated
runtime returns. The bridge does not reinterpret normal payment states or use
new polling behavior. Existing lock semantics are retained; the separate 6BC
architecture correction still owns insert timeout ordering and provider I/O
outside transactions.

## Verification

`scripts/tests/saas-billing-rollback-bridge.test.js` uses signed loopback HTTP,
independent real PostgreSQL connections and mocked provider functions. All
external fetches are forbidden. It verifies marked rollback fixtures for all
three nonterminal states, exact row/marker preservation, no event UPDATE,
terminal duplicates, 6D outcomes, signature ordering, protocol false positives,
concurrent deliveries, response/log safety and payload-marker injection.

Historical `received` / `failed` / `processing` controls execute both this
bridge and the exact production service/repository/controller loaded from Git
in memory. Responses, provider calls and resulting business state must agree;
transaction timestamps are checked against their own persisted row. Unmarked
BILL-004 recovery and BILL-005 retries are exercised as well.

Run production billing suites BILL-001, 002, 003/004, 005, 006A and 006D plus
the bridge suite. Use only an isolated loopback PostgreSQL database through
`BILLING_TEST_DATABASE_URL`; never point these tests at production. The bridge
test additionally enforces hostname `127.0.0.1` and user `billing_test`.

Local verification on 2026-10-02: 161 passed, 0 failed, 0 skipped across the
eight suites below. The bridge contributes 25 runner tests (22 PostgreSQL/HTTP
scenarios, two parser tests and their integration container). Concurrent marked
deliveries used two independent PostgreSQL sessions and completed in 77 ms,
with zero provider GETs and zero business mutations. These timings describe
the local fixture, not a production latency guarantee.

```powershell
node --test --test-reporter=tap scripts/tests/mercado-pago-diagnostics-readonly.test.js scripts/tests/mercado-pago-webhook-signature-enforcement.test.js scripts/tests/saas-billing-durable-provisioning.test.js scripts/tests/saas-billing-webhook-retry.test.js scripts/tests/saas-billing-contract.test.js scripts/tests/saas-billing-contract-postgres.test.js scripts/tests/saas-billing-contract-outcomes.test.js scripts/tests/saas-billing-rollback-bridge.test.js
```

Production `/__build` was rechecked and remained at the base SHA above. No live
production schema query was performed; column suitability was verified from
the deployed base's migration/repository and the real isolated PostgreSQL schema.
